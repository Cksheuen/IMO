# 让读者沿一个具体问题读懂链路

只在编写或修改调研/TRD 内容时加载。这里约束解释方式；事实核验、评论操作与画板契约继续使用现有规范，不另建流程。

## 一段结论、一条实例、按需钻取

先说这项能力在页面或业务里做什么，再沿用户给出的输入说明变化：

`输入及来源 → 处理后的具体值 → 下游消费 → 响应字段 → 页面位置/行为`

- 结论下默认显示几段连贯正文。未点击任何节点时，也能读懂主链；关键语义不能仅存在于 hover、代码批注或折叠区。
- 优先使用用户的实际输入和响应，不换成更容易讲的例子。每遇到抽象名称，交代**它是什么类型、当前值是什么、下一步拿它做什么**。例如 `route` 是结构体，`poolKey` 是字符串，策略输出是配置实体数组；不能统称为“配置”。
- 先给这个输入的完整结果，再补会改变结果的条件、空值和回退。数组是否保序、字段是透传还是翻译、显示还是发送，必须具体说明。
- 样本只证明样本。没有真实数据就明确标为说明例；不要为了填模板编造响应，也不要求每个基础概念配运行样本。

## 遇到追问，修正造成误解的那一步

从“原解释 → 用户追问/纠正 → 修正后的解释 → 后续是否仍在追问”提炼表达要求。重复追问意味着前一解释尚不足；“ok，我理解了”只表示用户认可当时的解释，不证明解释正确，也不证明其余内容已理解。

把高频检查点写成通用规则，业务专名、配置值和 session 对照留在产物里。不要把整段聊天、排障过程、偶发细节或推测偏好变成常驻规范。

相似名词应就近对照：原始值与派生值、配置归属与执行服务、内容 key 与最终文案、接口响应与前端缓存。先说明各自作用，再用同一个实例串起来。避免仅给“主路径/兜底”“配置驱动”等定性词。

## 事实边界说在影响判断的地方

- 分开写**代码会怎样、配置能命中什么、本次样本实际返回什么**；分支数量、函数名、设计意图都不能证明线上命中率。
- 涉及配置错配或线上状态时，先核对环境和相应版本；历史查询不能冒充当前状态。源码调用也不等于本次请求一定执行成功。
- 上游失败要写实际后果：返回原值、空值、上次配置还是默认值，接口是否仍成功，页面是否仍有内容。不要只写“不影响运行”。
- 用户指出矛盾时，重新核对事实；不能为迎合纠正而换成另一个无证据的断言。重要修正给出“原说法哪里不准 → 当前结论及边界”，不保留冗长辩论。

## 正文、画板和源码各做一件事

正文负责含义和实例；画板负责模块边界、分支、顺序；源码负责核对。三者共用字段名和节点归属，不各讲一套。

总图只交接跨模块输入输出，子图展开本模块。分支独立画，不合写相互排斥的结果。节点正文解释这一步改了什么、下游拿到什么；沿用已有契约、代码批注与图规范，不再额外复制整条链。

`research-workbench` 使用 `answer` 放短结论，`readingGuide: string[]` 放默认可读正文，`explanations` 放节点细节，`details/evidence` 放补充和来源。简单概念无需硬套全部字段。

## 交付前的理解检查

超过 500 字且含字段分隔符、箭头、赋值等符号的连续内容，如果没有正确的分节、列表或表格，视为表达不清晰，必须先优化。不能只把同一大段文字挪到另一块面板。概览按职责和分支分节；参数来源用“字段 / 来源文件与函数行号 / 赋值或回退”的表格，直接链接源码位置；比较行为用对照表。代码与字段名用行内代码，不把整条链重复堆进每段说明。

研究页支持 `readingSections` 与节点 `inputSources`，由 `rich-content` 公共组件排版。发布前运行 `node scripts/audit-research-readability.mjs <spec.json> [report.json]`，并目视核对实际页面。500 字检查是最低门槛，短于 500 字仍可能需要重写。


用本次用户问过的关键问题回查产物：不点画板能否回答“做什么、这个输入变成什么、在哪里看到”；点击对应节点能否核对中间值和代码；是否仍混淆来源或把推断当事实。把对照结果留在本次产物，不增加常驻验收台账。

优先沿用 Icarus CLI/SOP 的校验与回归；仅当它们无法判断实际展示时使用 Computer Use，不临时发明另一套浏览器验证流程。机器检查能确认内容覆盖和行为，不能保证读者实际理解，最终理解仍以用户反馈为准。
