# 评论列表批量处理，逐条认领

页面不提供处理按钮或自动连接提示。用户在当前对话要求处理评论后，Agent 原子提交一个批次，包含已保存、未解决、尚未处理的用户意见；重复请求复用活跃批次。列表保留「未解决 / 已解决」；未解决下分「待处理 / 处理中」。排队和已认领条目在处理中分组，处理完成后回到待处理分组并置顶；不再按当前场景或待复评筛选。

排队条目显示时钟，Agent 认领后仅对应条目显示处理中图标。处理完成且没有新意见时显示「待审阅」，按完成时间倒序置顶。用户编辑正文、追加回复或变更选区后，该新版本仍待处理。人审状态与处理状态分离：Agent 不自动标记 resolved；失败不冒充完成。

## 当前任务的 Agent 工作顺序

由当前对话的 Agent 通过本机 CLI 认领并更新每条状态，不自动唤醒任务、不创建后台 Agent、不用等待或保活消息维持模型运行。页面只读取处理进度；既有队列保留，排队不等于已开始处理。

实现前按 [Mod 实现规范](mod-implementation.md) 确定每条评论的功能所有者；评论协议与 UI 留在内核，画板、代码、Mock 等改动落到各自 mod，并验证独立入口与复合消费者。

## 以最新用户意见作为验收依据

认领后必须读取 `input.comment`、全部 `input.replies` 中 `author=user` 的追评，以及各个选区的文字和位置。不要只摘取顶层 comment；Agent 旧回复不是完成证据。将最新追评整理成可观察的验收条件，覆盖初始要求中已被用户纠正的部分。

例如：用户追评要求删除“执行顺序 ·”前缀，验收是实际连线文字不再包含该前缀；框选“逻辑关系”并说只有一个主题，对象是画板视图切换，不是节点的前端/后端标签。先核对选区对象，再决定 core/mod/数据落点。

`finish` 前必须对当前生成页验证这些验收条件。旧测试日志、队列 `verified:true`、构建成功或已有 Agent 回复均不能替代当前页面的行为证据。测试断言也必须服从最新用户意见；不能让过时断言继续要求用户明确要求删除的内容。用户指出此前完成结论错误时，可对相关条目重新 queue/claim，并在新回执纠正旧结论，保留历史与人审状态。

## 同类反馈的全局覆盖

逐条认领限定的是评论版本与回执归属，不是只修该评论的局部选区。沿用 David 的同类反馈闭环：先把症状归为可检查模式，在原 HTML/spec 中盘点所有页面、主节点、子图与相关展示层；逐项记录「已有 / 本次补齐 / 不适用及理由 / 未核实」。共享交互修 core/mod，业务函数、字段与调用事实修数据。所有适用位置都完成结构覆盖，行为变化再补针对性浏览器验证，不能以单点截图或“组件支持该字段”替代全体数据覆盖。

函数/文件解释遗漏时，核对每个执行节点的主函数、真实源文件分组、调用或数据边，以及绑定到具体函数的输入→处理→输出。多阶段初始化与请求执行分别表示，React effect/事件回调据实命名，不编造直接调用。只有部署盘点等非执行节点可使用 `flowExclusion` 写明理由。运行 `node scripts/audit-research-flows.mjs <spec.json> <coverage.json>`，清零适用范围内的遗漏后再回写；无法取证的范围必须明确记录，不能靠复制总览图或随意排除消除缺口。细则见 [研究工作台](research-workbench.md)。

发布前重读评论，保留并发用户新增内容；回执说明全局覆盖数量和仍未核实的边界。默认不因此扩大到无关项目，不修改用户人审状态。

## Icarus 全局完结门

这条是评论系统本体的统一要求，不属于任何单独 mod。评论只是发现问题的入口；收到一条评论后，先按症状盘点当前 HTML/spec 的全部页面、共享内核、已启用 mod、同类节点和生成展示，再处理适用的所有问题。不能因为评论只框选一个节点，就只修改该节点；也不能因为某个 mod 已通过自己的局部测试，就跳过全局检查。

每条任务在 `finish` 前都必须完成四项：

1. **归类**：记录该问题属于 core、共享 mod、业务数据还是资源事实，并列出受影响范围。
2. **覆盖**：逐页检查同类位置，标为已覆盖、明确不适用（写理由）或待核实；同类缺陷不能留在未分类状态。
3. **验证**：对共享交互跑受影响的独立 mod 和复合页面验证；对数据／代码问题核对来源、锚点、函数和输入输出；对无法验证的外部权限保留缺口。
4. **回读**：重新读取评论和源版本，确认并发新增内容没有被覆盖；回执写明全局覆盖数量和剩余边界。评论仍保持 `open`，直到人审。

模块规范只能声明模块内部的补充检查，不能替代这条全局完结门。没有适用模块时，仍然要执行 core 的全局检查；只有确实属于模块能力的修复才落到对应 mod。

收到「处理评论列表」后，读取已有批次。如果没有活跃批次，且该消息明确授权处理全部新评论，先 queue-all。沿用当前任务稳定 session ID：

```bash
icarus feedback task list <document-id>
icarus feedback task queue-all <document-id>
# batch-id 取自返回的 batch.id；next 原子检查最新保存内容并认领一条。
icarus feedback task next <document-id> <session> <batch-id>
# 返回 input 固定快照、entryId、id（task-id）。按该快照修改与验证。
icarus feedback task heartbeat <document-id> <entry-id> <session> <task-id>
icarus feedback task finish <document-id> <entry-id> <session> <task-id> "改动与验证结果"
# 无法完成时明确回写失败，继续其他条目；同一批次不无限重试失败项。
icarus feedback task fail <document-id> <entry-id> <session> <task-id> "原因"
# 每完成或失败一条，再执行 next；返回 batch.state=done 后结束本轮。
icarus feedback task next <document-id> <session> <batch-id>
```

1. 一个文档同时只认领一条。活跃批次中新评论保存时，与评论在同一次原子写入中入队，直接进入「处理中」分组显示排队状态，不必等待 Agent 领取下一条。排队中内容更新同步替换未认领快照；next 再核对并认领。当前正在处理条目的 input 快照保持不变。
2. 处理中同条出现新意见时，finish 只覆盖旧版本，标记 changed；下一次 next 为新版本创建任务。不能把全列表一并标为完成。
3. 已处理版本即使人审状态仍为 open，也不再次执行；旧评论已有最后一条 Agent 回复且没有新意见时同样跳过。失败项在同批次只尝试一次；用户再次在对话中要求处理才允许重试。
4. next 判空与批次结束同步落盘，队列清空后停止，不挂等待或轮询保活。结束之后新增的评论等待用户下一次在对话中要求处理。
5. 相同问题的相关代码可一起修复，但只回写实际覆盖的当前评论。未保存草稿不进入队列。
6. task-id 必须使用本轮 claim/next 返回值，禁止推断“最新任务”。CLI 私有保存认领凭据；页面不暴露凭据。五分钟续期，二十分钟租约；heartbeat 同时延长当前批次。
7. finish 原子追加 Agent 回复并结束该轮，重复提交幂等。失效凭据、过期租约、删除条目不能回写或复活；用户主动解决的评论不会被改回 open。
8. 认领冲突不抢占。状态不替代 Git 文件锁，外部同时改源码仍需协调。

## 本机协议

`GET /feedback/<document-id>/tasks` 返回公开 tasks、输入版本和 batch。`POST` 增加 `queue-all` 与 `batch-next`；保留 queue/cancel/claim/heartbeat/finish/fail 供定向 CLI 与旧客户端使用。David 浏览器适配仅允许 queue/cancel/queue-all，认领与结束仍使用 Agent 通道。新能力标识为 `feedback-batch-v1`。

任务和批次元数据保存在同一评论文件的 feedbackTasks / feedbackBatch 中，不改严格的 david-feedback/v1。所有浏览器状态以服务回读为准；排队成功、Agent 已认领、处理完成三个阶段不可混用。

React 工作台保存后立即更新任务状态；页面可见时以 500ms 间隔读取轻量任务快照，版本变化触发评论回读，相同快照不重复更新组件。用户主动选择的列表不会被新批次覆盖，展开中的条目保持可达，后台更新保留输入焦点、光标和可保留的列表滚动锚点。

新增评论的最新一个未提交草稿按 review slug 缓存在本机浏览器，包括正文、类别与原选区。关闭或刷新后重新打开反馈面板恢复；成功提交或清空正文后删除缓存。草稿不进入本机评论服务或处理队列，不表示已经提交。修改意见输入框随文字平滑增高，接近窗口剩余可用高度时停止增长并内部滚动，预留提交按钮与状态提示的位置；系统减少动态效果时取消动画。
