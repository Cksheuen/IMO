# 从资料提取必要信息

首次生成、补充设计资料或检查遗漏时使用；局部修改只核对受影响功能与引用。提取检查是工作过程，不是新的 review schema，也不要求额外生成一页审计正文。

## 1. 先划定业务范围

1. 锁定页面、功能与目标端/版本。设计截图按业务内容、宿主导航/安全区、系统状态栏、设计工具装饰区分所有权。
2. 默认不把时间、信号、电量、工具标尺等非业务外壳提成 `components`、mapping 或契约字段。仅为理解场景需要的外壳放在预览上下文；用户要求整机效果或业务自行实现的导航等按证据保留。
3. 以业务内容区域核对布局坐标，保留真实安全区和宿主占位，不能删除状态栏图形后直接沿用整张截图坐标或一律减固定高度。
4. 读取当前已有原始设计资料、PRD、已确认对话、代码/IDL 与运行证据；资料库按页面查询，见 [design-materials.md](design-materials.md)。当前 JSON/HTML 只帮助定位，不能反过来证明原设计没有其他内容。

## 2. 按原子项列源，再决定 JSON 落点

先从来源列出本次范围内的业务元素、动态内容和触点，再写 JSON。工作记录只需：

| 原子项 | 来源与状态 | 所属功能 | JSON 落点 | 处理结论 |
|---|---|---|---|---|
| 商家卡头像 | 设计图可见；接口未定 | 商家身份 | 所属契约字段 + 最小元素锚点 | 已覆盖，字段为 proposed |
| 标题下的视频入口 | PRD/交互稿 | 视频说明 | 功能交互与预览触点 | 核对打开、关闭/返回 |
| 系统电量图标 | 宿主截图 | 非业务外壳 | 不进入业务 JSON | 按范围排除 |

来源可记链接/文件与局部位置，不复制全文；同类重复元素可批量记录，只单列结构或行为不同的变体。结论为已覆盖、明确排除并说明理由、待确认。按信息类型加载 [数据](authoring-data.md)、[组件/交互](authoring-components.md) 或 [工程准备](authoring-preparation.md)。

## 3. 正向查漏，反向裁减

- **来源 → JSON**：逐项确认有所属组件/功能及正确字段；重点看重复卡片的商家/主播身份、头像、徽章、完整标题、媒体、跳转和操作结果，不能只覆盖第一张卡片或标题中的数字。数组/对象须能追到必要子字段；仅把 `array` 改名为 `ProductItem[]` 不算补齐。
- **JSON → 来源/用途**：每项字段、节点和技术说明应有实际消费者或评审用途。检查是否误加前端状态为后端字段、重复字段全表、无独立内容的父层总结、常规样式说明、没有证据的缓存/频控。
- **触点 → 行为**：核对初始状态、触发、条件、结果与关闭/返回；跨页/弹层逐条核对目标。仅写来源支持且影响当前判断的分支，不为填表臆造异常、持久化或兜底策略。
- **增量 → 同类位置**：用户指出一种模式时，核对本次 review 的其他页面与同类节点；无关功能保持原样。已确认的用户纠正不能因模板升级重新被旧样例覆盖。

## 4. 完成前核对

所有范围内原子项都有处理结论；必要事实、待确认项和引用可追溯；没有把提案当 confirmed；重复说明只保留一个主要承载。缺失资料先自行查找，仅在无法查明且阻塞当前任务时提问，沿用已有授权和概念模式边界。

随后按 [增量与候选验证](authoring-incremental.md) 校验结构与实际产物。`node scripts/audit-review-authoring.mjs <review.json>`（在 `<canonical>/project`）只提示假控件、长摘要、代码外说明与泛化类型；它不读取原始资料，不能证明字段/行为完整，零提示不能替代以上检查。交付只给简短覆盖结论和未验证项，不把整张工作记录塞进 review 正文。
