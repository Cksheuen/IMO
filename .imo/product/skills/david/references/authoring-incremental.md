# 增量修改与候选验证

修改已有 review JSON、处理评论或升级模板时使用。输出只给受影响片段；验证对象始终是合并后的完整 spec。

## 锁定对象与影响范围

1. 确认真实 spec 绝对路径、slug、产物路径与目标 page/component/node；已有 review 不另起同名 JSON 或更换 slug。先用 `review-context.mjs` 取目录与相关正文；只有 HTML 时核对 source.status，不能把快照或 sourcePath 当作已确认写回源，见 [read-review.md](read-review.md)。
2. 保存当前基线内容或摘要 hash，在候选副本/内存上修改；有 `collaboration` 时沿用 ownership/patch-only 协议，见 [collaboration.md](collaboration.md)。canonical 源码改动仍持有 SKILL 的租约。
3. 查目标功能的契约引用、字段锚点、mappingIds、技术代码与页面跳转等依赖；仅加载相关编写规则。反馈触发时同时盘点其他页面中的同类模式，见 [feedback-fix-workflow.md](feedback-fix-workflow.md)。

## 最小改动与验证

先按真实改动选择路径；“处理评论”或“包含画板”本身不触发引擎修改或浏览器操作。

| 改动类型 | 写入与验证 |
|---|---|
| 文案、字段、契约、功能拆合、技术代码、画板节点/边/说明 | 只修改源 JSON 的对应字段（包括 `graph` / `codeFlow`）；校验完整 spec、引用和受影响内容，复用当前模板渲染，无需重建 bundle |
| 业务预览的结构或样式 | 确有预览变化时才改 JSON 内的 `pageHtml`，保留声明式锚点，再生成 HTML；不直接编辑生成产物 |
| 共用渲染器、布局或交互缺陷 | 修改对应 React/CSS/脚本，按 [维护规范](maintenance.md) 跑受影响定向回归；只有模板运行时代码变化才重建 bundle |
| 仅编写规范 | 核对条款一致性、链接和适用场景；不构建模板、不重渲染业务页、不运行浏览器 |

- 评论从本机 CLI 读取；默认先用 `since` 获取增量，再按需要读取条目。方案用 `review-context --select` 读取目标及必要依赖，同类盘点在源 JSON 中完成；完整 spec 可供程序解析，不把整份 JSON、完整浏览器树或无关源码反复输出到上下文。
- “核对实际产物”先检查生成数据、引用、锚点和源 hash；更新已有预览地址时可用 HTTP 响应与磁盘产物比对。只有行为或渲染器发生变化，才补相应的已有定向自动化回归，不为纯内容改动重复执行浏览器导航。
- Computer Use 默认不用。只有明确的视觉疑点无法通过源码、产物检查或定向测试判断，或用户明确要求浏览器操作时才使用。使用前说明要判断的具体问题，聚焦对应区域，取得足够证据即停止；不把截图、滚动、跳转和整页浏览作为固定收尾步骤。
- 定向检查通过后，不再用 Computer Use 重复验收同一结论。仅新改动、检查失败或明确的剩余疑点可触发补验；额外验证仍限于该问题，不扩成全页巡检。图形本身的数据调整不等于需要视觉验收，几何布局等无法静态判断的问题才适用上述例外。

## 关联内容同步

同一功能的正文、技术代码、`graph` / `codeFlow`、契约引用、预览与子节点是同一行为的不同表达。变更前沿函数调用、状态条件、字段和 `mappingIds` 盘点消费者；有影响就同步更新，不用只改一段文案代表完成。无需变化的层保留原状，不为凑齐层级复制代码。

- 判断条件变化：核对分支节点、边标签、调用代码与注释；例如首次进入打开视频，画板必须呈现首次判断、播放调用和关闭返回，不能只修改 PRD 说明。
- 替换协议：同步清理旧 `contractIds`、API 文本与最小元素 `data-api-field`，区分真实响应字段与前端 ViewModel；未确认的新字段仍单独保留，不能错误映射到近似字段。
- 合并或删除代码：修复 `codeFlow` 节点、调用方、注释行号和相关子节点；完整实现只保留一个主要落点。
- 评论同步：方案、IDL、复用结论或缺口变化后，按[评论与当前方案对账](feedback.md#评论与当前方案对账)复核受影响旧条目；即使 `since` 无增量，也同步 Agent 正文中的已解决项、遗留项和替代关系，不能只追加回复。纯评论变化不触发重渲染。
- 验证记录按本轮受影响功能核对来源 → JSON → 生成 HTML；默认用结构和引用检查，不把逐页 Computer Use 变成固定步骤。

## 标明片段位置

下表是按 id 定位的作者说明，不是可直接交给解析器的 JSONPath 或新 patch schema；实际文件结构与 CLI 参数以源码为准。

| 定位说明 | 指向 |
|---|---|
| `openQuestions#<id>` | 待澄清条目 |
| `apiContracts#<id>` | 契约 |
| `components#<id>.mapping#<rowId>` | 根组件的一行 mapping |
| `components#<id>.children#<nodeId>` | 递归 children 节点；更深层写完整祖先链，节点自有 mapping 同样按 id 定位 |
| `pages#<id>` | 页面/scene |
| 元素 `data-*` 锚点 | pageHtml 内的最小变更位置 |

每段注明 `add/update/remove`；默认优先行/节点粒度，确需调整整个组件才输出组件段。契约与正文同改时给相关组件片段与契约片段，保留稳定 id；字段迁移执行 [authoring-data.md](authoring-data.md#契约迁移)。

## 先合并，再验证

1. 在当前基线上应用片段，确认引用目标在候选完整 spec 中存在；不发依赖隐含上下文的半截 JSON。
2. 对**合并后的完整 spec** 执行 `parseReviewSpec`。它要求 title/subtitle/components 等根数据，不是独立 mapping/contract 的校验器；不要为“片段独立通过”补一套无关页面骨架。
3. 执行受影响范围的来源 → JSON 和 JSON → 消费者检查：字段完整、同义内容无重复、数据归属正确、锚点与行为目标可达。编写审计只作提示，不能替代此步。
4. 渲染候选：`cd <canonical> && node scripts/render-review.mjs <candidate.review.json> <user-workspace>/<candidate>.html`；按[最小改动与验证](#最小改动与验证)核对实际产物中的受影响内容、引用及旧评论锚点。改到交互/布局时再验证对应行为，不默认打开浏览器；示例通过不替代当前产物检查。
5. 写回前重读目标基线；有变化则保留对方修改后重新合并并验证，不静默覆盖。只合入已授权的目标片段，重渲染正式产物。

删除业务节点时检查其引用与历史定位，默认不删锚点；用户明确要求删除时按实际范围清理依赖并说明定位变化，不保留悬空引用来假装兼容。

## 模板升级与内容改动分开判断

- 用户说“David 更新了”时，先核对模板与本次用到的编写规范是否变化。只有渲染器变化则保留原 spec，使用当前模板重新渲染；需要构建模板时在 canonical project 持租约执行，不手改 bundle。
- 编写规范有变化时，只调整受影响字段/功能及其引用；不得用旧 sample 全量覆盖用户修订或恢复已删冗余内容。
- 只改 Skill Markdown 不会改变浏览器渲染器；规范维护做链接、示例和任务使用验证，不声称业务页面已因此更新。
