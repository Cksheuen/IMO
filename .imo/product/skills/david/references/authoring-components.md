# 组件、交互与正文编写

修改功能设计、组件选型、技术正文、埋点或样式表达时使用。字段类型见 [review-schema.md](review-schema.md)，信息去留先遵守 [编写入口](authoring-json.md)。

## 按组件与职责归组

- 同组件的数据结构/契约引用、交互、埋点、代码结构和 TRD 讨论放在同一组件段；内部按 mapping 行组织。不要拆成全局“数据层 / 埋点 / 页面结构”三章。
- 父节点只承载组合职责，子功能进 `children`；按职责精确选择 `mappingIds`，不在多层重复整行内容。只有一行的叶子直接在父层显示，避免内容相同的中间层；节点交互与兼容规则见 [review-tree.md](review-tree.md)。
- mapping 已讲清行为和状态时，不生成同义 `deepDive.summary/logic/state`。每个条目只讲一项动作或规则，使用有序/无序列表与 `text + sub`；短文直接显示，复杂代码再展开。
- 产品列只写用户行为和结果；前端分支、接口参数、复用限制及调研证据分别归入技术、契约和来源。摘要已经表达的行为不再改写成一组 bullets。
- 未发生代码、配置或接入改动的既有入口/行为，不独立列为一个实施项；必要上下文并入真实改动行的注释或源码引用。由配置新增的内容使用配置或数据示例说明实际增量，说明展开等未改动行为随所属字段解释。
- 已有代码时，函数/属性解释进入 `codeAnnotations`，不得再复制为代码外 bullets 或需求点。尚未进入实现设计、纯风险或无需改动的来源说明可以用简短条目；涉及新增/改造行为必须补到输入、判断/转换、调用和结果更新可评审的具体代码，不能以暂无代码为由只留条目；现有 before/after 两侧均可配置代码注释。
- `codePaths`、chips、cross 等行级元信息按既有分层只显示一次。必要证据保留可达，常规工作日志与工具自身实现细节不混进业务正文。

## 复用选择先验证，再写结论

1. 按触发入口、展示/交互结果与数据契约确定候选身份，避免因同叫 Copy Link、Sheet 或 Video 就混用不同功能。
2. 核对目标仓库公开导出、props、真实消费者调用分支与端/版本；内部源码存在不等于可公开导入。目标是 Lynx 时，用该版本源码或官方依据核对组件/属性，不能以网页预览可用证明原生实现可用。
3. 比较本次需要的样式、行为和数据差异，做出以下选择；正文只保留影响选择的证据与结论，不铺整个调研过程。

| 选择 | 判定与应输出内容 |
|---|---|
| 直接复用 | 现有消费者可直接满足需求；配置驱动场景给真实字段及其生效链，改配置即可生效 |
| 小范围改造 | 需要新增类型白名单、条件分支、路由或 props 接线；即使内部使用已有组件，功能仍标为改造，给具体增量与共享消费者影响 |
| 迁移副本 | 共享组件改动过大但局部结构仍有复用价值；说明迁移范围、差异与维护责任 |
| 新建 | 候选不匹配或适配收益不足；说明缺口及组件边界 |

4. 迁移副本并在目标仓修改时用 `changeBlock.kind=migrate`，before 为来源、after 为目标实现；标签与方案摘要都标迁移，不暗示直接修改原模块。改动既有实现时用 `changeBlock` 展示真实差异：add 只有 after、modify 双侧、remove 只有 before，rationale 写原因；代码行解读进注释。不得用大量同义文字替代具体改造。
5. 区分业务方案的复用选择与 `components[].source` 的预览来源。真实组件/CSS art 两条还原路径仍按 [generation.md](generation.md) 执行；预览暂用 CSS art 不等于业务实现必须新写。

配置复用结论同时列明后端配置字段、HTTP 字段和前端消费位置。组件导出、前端硬编码白名单或 schema 常量不称为“后端配置”；若需先修改它们，明确改造后才可由下发字段触发。

- 配置能满足的文案、顺序、状态与既有组件行为，只输出需要修改的配置字段及示例，不新增前端登记模块、包装组件或状态钩子。一个授权行的开关、说明和 Learn more 放在同一功能点。
- 最小改动允许把稳定类型集合提取为同文件的具名 const，便于维护；不因此另建登记模块。
- 专属类型/路由确需接线时，只改已有白名单或路由分支。后端字段配置与前端硬编码的边界依源码说明，不把必要接线扩大成新配置系统。
- 存在可选 `trackParams` 不等于本次必须新增参数。沿用现有埋点；只有明确的本次埋点诉求或已确认错误才增加改动，并写明实际消费者。既有折叠/展开已满足需求时，优先配置合适文案并验证多语言展示，保留原组件。

## 逻辑画板与实现覆盖

- 组件控制关系、条件分支和跨模块接入流程使用 `techPoints[].graph`，复用共享 LogicCanvas；禁止用 ASCII 箭头或代码富文本伪装图。节点的 `description[]` 说明职责、输入/输出和边界，悬停/键盘聚焦可读。具体代码另放同一功能的代码块，不复制同义说明。schema 与布局见 [tree-canvas.md](tree-canvas.md)。
- 处理“缺少具体代码”时先用 `audit-review-authoring.mjs` 的 `implementationInventory` 逐页逐行盘点，包括 inline child mapping；每行记录补齐、已有完整实现或无需代码及原因。非空字符串、调用未定义占位函数和语法通过均不等于实现完整。检查主要依赖/类型有来源、props 与消费者匹配、成功/失败/取消/并发分支可评审。
- 对 `onOpenProduct`、`onOpenShop`、`onDone` 等回调，必须指出并给出实际默认实现和消费者绑定，不能只声明 props 或再包装一层未定义函数。相同动作统一到共享模块，引用真实 SDK/schema helper；接口未确认时明确缺口，不编造端点。操作链沿“触发 → 参数 → 实际调用 → 成功/失败结果”核对。
- 一组组件迁移用一组连贯 before/after，加行注释；共享实现跨页引用同一责任模块，消费者仍给调用适配，不复制多套实现。未分配 IDL 枚举、未登记路由与未确认后端字段保持提案边界，不能为凑代码猜值。

## 每个触点形成行为闭环

为来源中出现的操作核对初始状态、触发条件、状态变化/结果、关闭/返回，以及需要传递的数据。按实际范围逐项检查按钮、整行点击、折叠、分享、跨页和弹层，不能只写“存在一个 sheet”。状态责任按 [authoring-data.md](authoring-data.md) 判定；没有证据的频控、缓存和异常策略不要自动补入。

- 产品行为写入所属功能的 `trd`；代码解释用 `techPoints[].codeAnnotations`。避免把 icon 名称、`data-review-overlay` 实现方式逐项写成业务需求。
- 可演示技术点可声明 `techPoints[].preview = { overlayId: "已有 overlay id" }`：打开详情临时预览，关闭恢复之前状态。触点与目标锚点必须存在；不得注入任意脚本。
- 跨页、原生打开/返回或分享等行为以业务源码/契约为依据；静态 HTML 模拟不能当作原生能力验证。

## 埋点与触发处一体化

在触发元素挂 `data-track-event`，事件和参数以来源为准；无来源时标待确认，不能猜注册值或把示例当真实事件。埋点与触发组件/字段相邻，不另建集中章节。

```html
<button data-review-target="confirm-btn" data-track-event='{"name":"ticket_confirm","params":{"coupon_type":"couponType"}}'>确认核销</button>
```

上例仅演示声明格式。代码块内埋点行用 `~ `，与改动行 `+ ` 同为行级标记，特殊高亮且默认折叠；保持单一代码块与连续行号：

```text
  const ticket = useTicket();
+ const onConfirm = () => submit(ticket.id);
~ track("ticket_confirm", { coupon_type: ticket.couponType });
  return <Button onClick={onConfirm}>确认核销</Button>;
```

参数引用字段时仍保留该字段的最小元素锚点。埋点完整参数有评审意义，但完整 Mock response 没有因此进入正文的必要。

## 样式与装饰取舍

- 常规尺寸、颜色、圆角、装饰层和样式代码由设计稿与预览承载，不铺进技术正文；保留影响行为、兼容性或布局责任的约束。
- 业务项目沿用其技术栈，常规样式默认使用项目支持的 tailwind utility；非必要不加内联 style 或独立 CSS，不因套用此默认值而引入项目不支持的语法。
- 业务预览中不添加参数演示器、渲染机制说明、评审免责声明或状态示例脚注。跳转参数、状态规则与来源事实写在所属组件设计/技术代码中；界面只呈现产品内容，不在组件上下额外堆说明。
- David `pageHtml` 是自包含静态产物，没有 tailwind 运行时；使用内联 `<style>`、唯一类名前缀与设计 token，component/drilldown 根样式自足。不要混用两种产物的规则。
- 不写只为命名的装饰 class。类名只承担实际样式隔离或引用责任。
- 保留 `data-component-id`、`data-review-node-id`、`data-review-target`、`data-review-label`、`data-api-field`、`data-track-event`、`data-page-id` 与 `data-review-overlay*` 锚点。字段改名同步更新关联 token，按 [契约迁移](authoring-data.md#契约迁移) 与增量规则验证，不删掉锚点能力。

### 多代码与语义注释

同一功能有多个独立代码块时，先用 `technical.codeFlow` 说明它们真实的调用、数据或引用关系，点击可多选/取消节点，下方展示所选代码。为每个代码要点提供稳定 id；独立视图可通过共同宿主表达组合关系，不虚构函数调用。单个 before/after 对照仍是一个改动块。schema 见 [tree-canvas.md](tree-canvas.md)。

`codeAnnotations` 按实际语义边界分段：输入与类型、校验、转换、调用、结果处理分别对应相关行；不同功能不可放进覆盖整块代码的一条注释。每段只解释本段行为和必要约束，禁止机械均分行数、重复泛化说明或把整段要点挂在 import 上。短且单一动作的代码可以只有一段；协议字段已有专用字段说明时不重复铺满注释。审计中的 broad-code-annotation 需要人工核对语义，不能自动切块。

字段契约默认收起，保留接口名、路径和确认状态；标题/路径可展开，旧评论定位字段时自动展开，读者手动切换不被普通重绘重置。

概览的简要说明只放稳定摘要和详情入口；准备清单、输入表单等会撑开行高的操作放在详情/组件层，继续复用同一份本机填写状态。代码多选的增删应有尺寸与淡入淡出过渡，退出期间不可操作，快速切换和减少动态效果设置仍须正确。滚动时关闭代码悬停说明并暂停重开，停止滚动后再响应新的悬停/焦点；浮层自身的阅读滚动不受影响。

代码注释的行号只按本侧源代码计数，避开无关函数和空白边界；连续代码段共用一个边框，对齐占位与空白行不纳入。定位提示保留原底色与文字对比度；前后对照支持分别收缩，至少保留一侧可读，并兼容键盘与 reduced-motion。
